# Инструкции ИИ-агенту проекта WEP

## 1. Назначение проекта

WEP (Wepwawet ESP32 Profiler) — приложение для Windows, предназначенное для обследования ESP32, сбора доступных аппаратных сведений, сохранения результатов в JSON и генерации конфигурации PlatformIO.

Русское название: Упуаут — Профилировщик ESP32 (УПЕ).

Проект также служит практической площадкой для изучения разработки на Python и применения ИИ-агентов.

## 2. Среда разработки

- Целевые операционные системы: Windows 10 и Windows 11, x64.
- Текущая среда разработки: Windows 11 x64.
- Дополнительная среда разработки: Windows 10 x64.
- IDE: Visual Studio Code.
- ИИ-помощник: GitHub Copilot Agent.
- Язык программирования: Python.
- Виртуальное окружение: `.venv`.
- Контроль версий: Git.
- Документация: Markdown.

Инструкции по установке и рабочие процессы должны быть совместимы с обеими версиями Windows. Не полагаться на функции, доступные только в Windows 11, без явного согласования.

Архитектура приложения, GUI-фреймворк, диагностический протокол и зависимости пока не выбраны. Не считать предварительные варианты утверждёнными решениями.

## 3. Правила работы

1. Перед изменениями изучать существующие файлы проекта.
2. Перед нетривиальными задачами объяснять подход и перечислять предполагаемые изменения.
3. Предпочитать небольшие последовательные изменения масштабным переделкам.
4. Не добавлять без необходимости абстракции, фреймворки, зависимости и файлы конфигурации.
5. Не изменять файлы и проекты, не относящиеся к текущей задаче.
6. Объяснять важные технические решения понятным практическим языком.
7. Не утверждать, что команда, тест или операция выполнены успешно, без проверки результата.
8. Если неоднозначность существенно влияет на результат, задавать один конкретный вопрос.

## 4. Безопасность и выполнение команд

Обычные локальные действия разработки допустимы, если они необходимы для согласованной задачи и имеют ограниченный масштаб.

До выполнения необходимо объяснить действие и запросить разрешение, если оно предполагает:
- удаление или перезапись существующих пользовательских файлов;
- разрушительные операции Git или переписывание истории;
- массовые изменения несвязанных файлов;
- установку системного ПО или изменение системных настроек;
- установку новых зависимостей, необходимость которых ещё не обоснована;
- публикацию кода, отправку коммитов или изменение удалённых репозиториев;
- доступ к секретам, их передачу или раскрытие.

Не выводить секреты и не помещать пароли, токены, учётные данные или приватные ключи в исходный код и файлы, отслеживаемые Git.

Не использовать права администратора без явного согласования и реальной необходимости.

## 5. Окружение Python

- Использовать `.venv` проекта для разработки и тестирования.
- Не устанавливать зависимости WEP в окружение PlatformIO.
- Не добавлять `.venv` и кэш Python в Git.
- Перед добавлением зависимости объяснять её назначение.
- Предпочитать воспроизводимое управление зависимостями и документировать установку.

## 6. Достоверность диагностики ESP32

Различать:
- сведения, прочитанные непосредственно из чипа или существующей прошивки;
- сведения, полученные в ходе диагностического теста;
- данные, введённые вручную;
- предположительные или неподтверждённые сведения.

Не представлять предположения как подтверждённые факты.

Один только адрес I2C не позволяет установить точную модель подключённого устройства.

Не предполагать, что ESP32 может автоматически определить любую подключённую периферию, плату или электрические характеристики.

По возможности сохранять ошибки, предупреждения и сведения о неполных результатах обследования.

## 7. Конфигурация PlatformIO

- Не определять точный идентификатор платы PlatformIO только по модели чипа.
- Не добавлять библиотеки и параметры без достаточных оснований.
- Явно указывать предположения и нерешённые вопросы.
- Генерируемая конфигурация должна быть доступна для проверки и редактирования пользователем.

## 8. Тестирование и проверка

После изменения кода:
1. Запускать относящиеся к задаче тесты, если они доступны.
2. Выполнять дополнительные проверки, соответствующие изменению.
3. Точно сообщать, какие проверки проводились и прошли ли они.
4. Указывать проверки, которые не удалось выполнить.

Не изменять и не ослаблять тесты только ради того, чтобы неуспешная реализация выглядела успешной.

По возможности проверять совместимость с Windows 10 и Windows 11. Если доступна только одна система, прямо указывать, что вторая не проверялась.

Если тестов ещё нет, предложить минимальную стратегию тестирования, не создавая преждевременно избыточную инфраструктуру.

## 9. Документация

- Использовать Markdown.
- Документировать настройку проекта так, чтобы его можно было восстановить на другом компьютере с Windows.
- Фиксировать значимые архитектурные решения и причины их принятия.
- Поддерживать соответствие документации фактической реализации.
- Не заявлять о соответствии стандартам или спецификациям без проверки.
