# Диагностика

WEP использует esptool, чтобы получить ограниченные идентификационные данные
через выбранный последовательный порт ESP32. Команда диагностики — `read-mac`;
она запрашивает тип чипа и заводской MAC-адрес. WEP не читает, не записывает и
не стирает flash, а также не определяет внешнюю периферию и электрические
характеристики.

## Последовательность подключения

GUI запускает рабочий поток для выбранного порта. В обычном сценарии GUI модуль
диагностики вызывает esptool с параметрами
`--before default-reset --after hard-reset read-mac`. Стратегия
`default-reset` пытается сбросить плату и войти в ROM-загрузчик через
последовательный интерфейс. Результат зависит от платы и схемы USB-UART/reset.

API диагностики принимает необязательный аргумент
`manual_bootloader=True`, который меняет начальное поведение на
`--before no-reset`. Текущий GUI не предоставляет этот параметр: кнопка
диагностики всегда использует обычный `default-reset`. Поэтому то, что плата
отвечает только после ручного BOOT, само по себе не доказывает конкретный дефект
программы. Ручной вход в загрузчик и повторное нажатие кнопки GUI не включают
`no-reset`: следующий запуск всё равно запрашивает `default-reset` и может
сбросить плату из загрузчика. Чтобы установить причину несрабатывания
автоматического входа, нужно проверить разводку reset/BOOT конкретной платы,
USB-последовательный интерфейс и вывод esptool на физическом устройстве.
Нельзя считать, что WEP подтвердил автоматический reset платы без такой
проверки.

## Безопасность и тайм-ауты

Запуск диагностики может сбросить выбранную плату и прервать выполняющуюся на
ней прошивку. Перед запуском закройте другие программы, использующие COM-порт.

При обычном запуске Python esptool работает как дочерний процесс. В PyInstaller
esptool API запускается в дочернем процессе spawn, поскольку в frozen-приложении
`sys.executable` указывает на EXE WEP. Родительский процесс захватывает вывод и
исключения, ожидает диагностику до 20 секунд и пытается остановить зависший
процесс. Ожидание завершения дочернего процесса дополнительно ограничено двумя
секундами. Один только тайм-аут `join` не останавливает процесс: код отдельно
запрашивает завершение и проверяет, вышел ли процесс.

## Статусы результата

| Статус | Значение |
| --- | --- |
| `success` | esptool завершился успешно, из вывода извлечены тип чипа и MAC. |
| `partial` | Получены некоторые распознаваемые данные, но операция завершилась тайм-аутом, ошибкой или неполным ответом. Отсутствующие значения остаются отсутствующими. |
| `failed` | Не получены пригодные данные chip/MAC либо операцию не удалось запустить или завершить. |

Результат сохраняет выбранный порт, распознанные тип чипа и MAC, исходный вывод
esptool и код/сообщение ошибки, если они есть. Исходный вывод доступен в панели
результатов GUI. Профиль и экспорты сохраняют статус и происхождение данных, а
не представляют отсутствующие сведения как факты.

## Типичные ошибки

- **Нет последовательных данных / тайм-аут:** проверьте выбранный порт и
  USB-подключение. Может потребоваться ручной вход BOOT/RESET, если схема
  автоматического сброса не переводит плату в ROM-загрузчик.
- **Ошибка синхронизации:** проверьте выбранный интерфейс, подключение и
  подробный вывод esptool. Показанная ошибка сама по себе не устанавливает
  единственную причину.
- **Порт недоступен:** закройте serial monitor и другие программы, которые
  используют порт, затем обновите список портов.
- **Частичный результат:** часть значений получена, но успешный полный ответ
  отсутствует. Изучите ошибку и исходный вывод.
- **В EXE отсутствуют данные esptool stub:** проверьте, что в PyInstaller-сборку
  включены JSON-данные по ожидаемому относительному пути
  `esptool/targets/stub_flasher/`. Не используйте `--no-stub` как постоянную
  замену включению необходимых файлов.

## Ограничения диагностики

Поиск портов выполняется через pySerial и не открывает каждый порт, а также не
подтверждает наличие подключённой платы. Модель чипа не определяет точную
модель отладочной платы. MAC не идентифицирует периферию. В рамках операции
`read-mac` WEP не измеряет ёмкость flash, PSRAM, частоту, содержимое прошивки
или электрические характеристики.

Автоматические тесты диагностики используют моки дочернего процесса и
последовательного взаимодействия. Они не заменяют проверку физической платы.
Нельзя заявлять о фактическом соединении или успешном автоматическом BOOT
только на основании этих тестов.
