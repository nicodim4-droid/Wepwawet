# Настройка разработки

Для WEP используется виртуальное окружение проекта `.venv`. Из корня проекта
выполните в PowerShell:

```powershell
py -3.14 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Команда выберет Python 3.14, использованный в проверенной среде. Для запуска
исходников требуется Python 3.11 или новее; совместимость иных версий Python и
PyInstaller отдельно не подтверждалась.

Для запуска всех тестов:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Для запуска графического приложения:

```powershell
.\.venv\Scripts\python.exe run_wep.py
```

Для сборки Windows EXE используйте конфигурацию `WEP_Copilot.spec` из корня
проекта. PyInstaller — отдельный инструмент сборки, не указанный в
`requirements.txt`; проверенная сборка использовала PyInstaller 6.22.3 в
`.venv`. Если он ещё не установлен, установите его только в виртуальное
окружение проекта:

```powershell
.\.venv\Scripts\python.exe -m pip install PyInstaller==6.22.3
```

Команда сборки использует отдельные каталоги. Если они уже содержат результаты
другого участника, выберите новые имена вместо перезаписи:

```powershell
$distPath = 'dist\WEP_Redesign'
$workPath = 'build\WEP_Redesign'
if (Test-Path $distPath) {
    throw "Папка результатов уже существует: $distPath. Выберите свободный путь."
}
if (Test-Path $workPath) {
    throw "Рабочая папка уже существует: $workPath. Выберите свободный путь."
}
.\.venv\Scripts\python.exe -m PyInstaller --noconfirm --distpath $distPath --workpath $workPath WEP_Copilot.spec
```

Проверенная сборка создала `dist\WEP_Redesign\WEP.exe` с PyInstaller 6.22.3.
Конфигурация создаёт один EXE: в папке распространения находится исполняемый
файл, а PyInstaller распаковывает ресурсы во временную папку при запуске.
В EXE включаются графический знак WEP и данные stub-файлов esptool.
Исходник символа находится в `src\wep\assets\wep_symbol.svg`; приложение
использует подготовленное изображение PNG, а EXE — ICO.

Интерфейс использует стандартные Tkinter и ttk. Цветовая тема и язык интерфейса
сохраняются в `%LOCALAPPDATA%\WEP\settings.json` и не попадают в репозиторий.
Для новых установок язык интерфейса по умолчанию — English; язык можно изменить
в самой программе без перезапуска.
Если у установленной сборки Python отсутствует Tkinter, установите обычную
Windows-сборку Python с компонентом Tcl/Tk и повторно создайте `.venv`.

Тесты обнаружения последовательных портов используют моки и не требуют
подключённого оборудования.

Диагностика ESP32 использует `esptool==5.6.0` в отдельном процессе с тайм-аутом
20 секунд. Она запрашивает тип чипа и встроенный MAC через `read-mac`, не читая
flash и не выполняя операции записи или стирания. Перед запуском диагностики
плата может быть сброшена, что прервёт выполняющуюся прошивку. Автоматический
вход в загрузчик зависит от платы; если он не сработает, следуйте инструкции
BOOT/RESET с учётом ограничения: GUI не предлагает режим `no-reset`, поэтому
повторный запуск диагностики снова использует `default-reset`.

Тесты диагностики используют моки дочернего процесса и не требуют платы.

Исходный код использует `datetime.UTC`, поэтому требует Python 3.11 или новее.
Проверенная среда сборки: Windows 10 x64 и Python 3.14.2. Windows 11 отдельно
не проверялась. Проект не содержит конфигурации линтера или форматтера.

GUI вызывает диагностику с `default-reset` до операции и `hard-reset` после
неё. Режим `no-reset` существует в API диагностики, но не предоставлен
пользователю в текущем GUI. Ручное удержание BOOT может потребоваться в
зависимости от платы; фактическую причину следует устанавливать проверкой на
конкретном оборудовании. Тесты с моками не подтверждают поведение физической
платы.

Подробнее см. [архитектуру](./ARCHITECTURE.ru.md), [руководство пользователя](./USER_GUIDE.ru.md)
и [описание диагностики](./DIAGNOSTICS.ru.md).
